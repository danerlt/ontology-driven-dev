这里需要先限定“本体”的语境：我们讨论的是仓库自己的业务软件建模方案，使用 YAML 表达对象、行为、规则等语义。理解这个项目，并不需要先学习 OWL、RDF 或知识图谱推理。 它借鉴了领域模型、聚合和状态机等思想，但又把权限、流程、报表和界面入口纳入统一的引用体系。重点是分工和连接：规则定义一次，行为按 ID 引用；流程引用行为，而不是把行为内容抄一遍。 因此，YAML 的价值不在于格式本身，而在于结构化的定义、稳定的标识，以及可以检查的引用关系。

这是最容易被误解的一页。开发阶段，AI 或开发者依据模型和指导书生成、修改业务代码；运行阶段，应用启动时从 manifest 读取 YAML，建立注册表。 registry.py 的代码很直白：按 model_type 把对象、行为、规则、角色、流程、报表和屏幕注册到字典。它提供统一的语义索引。 但它没有因此自动重建所有数据库表，也没有动态重写 React 页面。收款联动仍是服务里的显式调用，很多规则仍是函数。 所以模型变更要走影响分析和测试。讲“模型即语义来源”是准确的，讲“这里已实现全自动 YAML 编译器或热更新低代码平台”则超出了证据。
